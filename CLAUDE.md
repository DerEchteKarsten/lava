# lava

Vulkan abstraction in Rust (stable, edition 2024) with bindless resources, automatic barrier tracking and typed pass bindings generated from Slang at build time. Its main user is the game engine in `../GameEngine` (`core` depends on `lava` and `lava-build-slang` by path); its docs show how the engine uses lava where that explains a design.

## Orientation: read this before exploring
- A **code map** (each file's purpose, key types, plus live git state) is injected at session start by a `SessionStart` hook, which runs the engine's `tools` generator (`../GameEngine/tools`) with `--root .`. Check it before running `ls`/`rg`.
- Full pub signatures and struct fields live in `.claude/context/api/{lava,lava-build-slang,lava-tests,lava-macros}.md` (`lava-tests.md` also lists the generated test pass bindings, from the newest debug build). Read the relevant file instead of grepping for an API.
- To refresh them by hand: `cargo run -q --release --manifest-path ../GameEngine/tools/Cargo.toml --target-dir ../GameEngine/target/tools -- --root .` (stable cargo, cached by mtime). The engine's own sessions map lava too (`--with ../lava`).
- **Subagents don't get the hook output.** When delegating exploration, tell the subagent to read `.claude/context/codemap.md` first.
- Known bugs, intended limitations and ideas for future work are listed in `STATE.md`; the publishing review is `lava/SURVEY.md`. Check them before debugging or designing, delete an entry when you fix or build it, and add bugs you find but don't fix and ideas worth keeping.
- Every `.rs` file starts with a one-line `//!` doc that feeds the code map. Keep it accurate when a module's role changes, and add one to every new file.

## Crates (dependency order)
- `lava-macros`: proc macros for lava (validation tracing).
- `lava-build-slang`: lava's Slang frontend, called from an application's `build.rs` (see Shader pipeline); compiles its Slang passes and generates their bindings and `PASS_MAP`. Its `slang/` (searched by every session) holds `bindless.slang` and `ray_tracing.slang`, the Slang side of lava's shader contract (the "Shader contract" section of lava's `lib.rs` docs: descriptor sets, push constants, handle and instance layouts), and `profile.slang`, shader clock helpers lava has no part in, whose readout it generates (see Shader clock regions). With its `hot-reload` feature (only as a normal dependency; the build script's copy never compiles lava) it also holds the runtime shader hot reload. The only crate that links Slang; lava has no Slang in any feature combination, so a frontend for another language (`lava-build-glsl`, see STATE.md) could sit beside it.
- `lava`: Vulkan abstraction over `ash` + `gpu-allocator`; it takes SPIR-V and has no Slang. Global `Ctx` state, bindless descriptors (`BindlessHandle`; lava keeps no index bookkeeping, see Bindless slots), `lava::init(Option<display>, validation, gpu_assisted, &PASS_MAP)` (`None` = headless; the application's pass map, see Shader pipeline), per-window `Surface` + `Swapchain` objects, usage-typed `Buffer`/`BufferSlice` and `Image`/`ImageView` (a `BufferSlice` is only what the GPU sees, an address, a size and the usage, borrowing its buffer; every command takes it as a `VkDeviceAddressRangeKHR`, so lava requires `VK_KHR_device_address_commands` and never passes a buffer handle or offset, and the flags each command takes come from the usage (`address_flags`: storage known or unknown, always fully bound); host access is `Buffer::host()`/`host_mut()`, plain `&[T]`/`&mut [T]` over the mapping, so sub-ranges and copies are std's and the borrow checker rules out aliasing, plus `host_ptr()` for buffers whose elements are owned one at a time through a shared reference (core's material slots), whose derefs are `unsafe` with the invariant stated at the call site; host writes racing GPU reads of a frame in flight stay a convention, the `frame_in_flight * MAX` rings) (type-state generics `F: Format`, `U: *Usage`, and for images `D: Dim` (`image/dim.rs`: `D2`, the default, or `D3`; extents and offsets are `D::Extent`/`D::Offset`, `UVec2`/`IVec2` or `UVec3`/`IVec3`) and `V: Views`: the default `Single` keeps one view, handle and tracked layout for all mips (render targets, textures), `PerMip` (`MipChain<F, U, D>`) adds a view, handle and layout per mip (`mip_view(level)`, `bind_mips_sampled/storage(first)` put mip `i` at `first + i`) for images whose mips the GPU accesses one at a time; `extent()`, `mip_levels()` and `handle()` are methods; commands only take `ImageView<F, U, D>`, which knows its mip range and the extent of its first mip, so `view.whole()` is that mip's `ImageSlice`; transfers work in any dimension, attachments and presenting take 2D views, and lava-build-slang gives each generated image parameter the dimension of its Slang `Img` shape (`Tex3D` needs a `D3` view); an image gets exactly its usage's flags, one marker type per combination Vulkan allows, generated by `usages!` in `image/usage.rs` and named by concatenating `ColorAttachment`/`DepthAttachment`, `Sampled`, `Storage`, `HostCopy`, `TransferSrc`, `TransferDst` in that order, e.g. `ColorAttachmentStorageTransferDst`; clears, copies and blits need `IsTransferSrc`/`IsTransferDst`; buffer usages are generated the same way in `buffer/usage.rs` from storage, uniform, vertex, index and indirect, and every buffer also gets device address and transfer src/dst, because leaving transfer out made no measurable difference, and acceleration structure build input when that feature is on (no measurable difference in the benchmark view either); besides these static types, `format::Dynamic(VkFormat)`, `image::usage::Dynamic(ImageUsageFlags)` and `buffer::usage::Dynamic(BufferUsageFlags)` are values known only at runtime that meet every bound: images and buffers store their `F`/`U` values, and every command buffer function and generated binding calls `aspect_check`/`texel_check`/`usage_check` with what its bounds require, which is empty for the `StaticFormat`/`StaticUsage` types and panics for a dynamic one that lacks it; clear values are lava's `format::ClearValue` (a `Dynamic` format takes one directly and checks its variant); `new`/`with_mip_levels` are for static types, `Image::with_params(format, usage, ..)`/`Buffer::with_usage(usage, ..)` take any, and `erase()` turns an image into a `DynamicImage<D, V>` (`Image<format::Dynamic, usage::Dynamic, D, V>`) and a buffer into a `DynamicBuffer` (`Buffer<u8, usage::Dynamic>`); the swapchain's images and core's viewport target have its runtime `format::Dynamic` (`Swapchain.format`), and `GpuTexture` is an `Image<format::Dynamic, SampledHostCopy>`), `CommandBuffer` with automatic barrier tracking (every image access asks for `GENERAL`, except attachments, which are in `ATTACHMENT_OPTIMAL` while drawn to; a pending write gets no second barrier for stages and accesses an earlier barrier already made it visible to, and a layout transition waits only for its image's tracked accesses, or for everything when there are none; each queue keeps the pending accesses of what was submitted to it (`FamilyQueues.pending`, locked while a command buffer for it is recorded and submitted, so leases sharing a queue record one after the other; `reselect` copies them to the new queue), and destroying an image or buffer forgets its accesses on every queue; an image's tracked layout is an atomic in the image (one per mip for a `MipChain`, one per image of a swapchain; a transition gets one barrier per run of neighbouring mips with the same old layout, and memory dependencies stay per image in the global memory barrier) that moves when an access is *recorded*, so bindings may be recorded in any order or dropped, but command buffers that share an image must be recorded one after the other and submitted in that order), and `compute`/`raytrace`/`raster` dispatch. A `Queue<Q>` is a lease on one queue of a family (`FamilyQueues` in `vkobjects/queue.rs`): `Queue::new()` takes one no other lease holds while there is one, then the least shared one, which leases take turns on (a `Mutex` per queue). `is_optimal()`/`reselect()` move a lease off a shared queue once another freed up (rare; it waits for the old queue to idle, so its slots stay valid). A frame loop submits its `FrameSlot`s through one lease, so its frames stay in order; core keeps its lease with its slots in the `FrameSlots` resource. A `SemaphoreInfo` (`Semaphore::info()`) is waited on at `ALL_COMMANDS` unless `.at(Stage::{Compute, RayTracing, Raster, Transfer})` names the kind of lava command that first touches what it guards, a hint the caller is responsible for: core waits for its swapchain image at the composite pass (`Compute`) when the scene is drawn straight into it, else at the UI rendering (`Raster`), so the frame culls and shades before the image is acquired; the transition out of `PRESENT_SRC_KHR` waits at `ALL_COMMANDS`, which chains with any wait stage. Every submission ends with a barrier that makes its writes host-visible (readbacks, clock counters). Host image copies (`Image::copy_from`) aren't synchronised with frames in flight. A generated `Pass::push_bindings(...)` returns a `Bindings<'a, K, P, I, B, C>` (a pass with specialization constants returns an `IncompletePass` that `.constant_bindings(...)` completes; the zero-sized `kind::{Compute, RayTracing, RasterVertex, RasterMesh}` marker decides where it can be recorded), sized by what the pass has: `P` bytes of push constants, `I` image and `B` buffer accesses (lava's `ImageUse`/`BufferAccess`), `C` bytes of specialization constants. It derefs to the unsized `BindingOutput<K>`, one run of bytes (header, push constants, image accesses, buffer accesses, constants) that commands borrow, so a call site writes `cmd.compute(&Pass::push_bindings(..), ..)` and can record one binding twice. A resource a pass reaches without naming it (through a handle or pointer in a buffer) is declared with `cmd.record_access(Access::{sampled_read, storage_read, storage_write, buffer_read, buffer_write, trace}(..), Stage::{Compute, RayTracing, Raster, All})` before the command (before the rendering for draws): it is tracked at once, and its barrier waits in the command buffer (`deferred`) to join the next command's, or the end of the recording. Index and indirect buffers are accesses of the draw or dispatch, not of the binding. A pass pushes only its own struct; `CommandBuffer::begin` zeroes the whole range once, so the validation layer never sees unset bytes. `cmd.raster(extent, [Attachment::color(view, clear), ..])` starts one rendering with its color attachments (at most `MAX_COLOR_ATTACHMENTS`), then `depth_attachment(view, clear)` and any number of `draw`/`draw_indexed`/`draw_indirect(_count)`/`launch(_indirect)` calls, each with its own `RasterState<COLOR_ATTACHMENTS>` (`blends([..])`, an array of one `Blend::{Replace, Alpha, Add, Attenuate, Skip}` per colour attachment, default all `Replace`; `depth_write`; `backface_culling`; `wire_frame`), and `record(name)` records them in one rendering under one GPU scope. Within a rendering, depth and blending follow draw order without barriers, but nothing else does, so no draw may read what an earlier one writes. `RasterBuilder<'a, N>` has the attachment count in its type, so a draw with the wrong number of blends doesn't compile; its methods take and return `&mut Self`, so draws can be added in loops, and they go into a list the command buffer lends each rendering and `record` takes back (no allocation per frame). Direct draws of 0 instances are skipped.
- Traits only lava implements (`Format`, `ImageUsage`, `BufferUsage`, `Dim`, `Views`, the aspect markers, `SemaphoreType`, `QueueFamilie`, `Level`, `IndexFormat`) have the supertrait `crate::sealed::Sealed`, a public trait in a private module: other crates can bound by them but not implement them, and their sub-traits (`IsSampled`, `HasTexels`, ...) are sealed through them. Seal new ones the same way; `VertexPosition` stays open for vertex types of other crates.
- Epochs (`lava/src/epoch.rs`): views, slices and `SemaphoreInfo`s borrow what they name (`Copy`, no count), and lava counts nothing per use. A frame reserves an `Epoch` (`epoch::reserve()`) before it reads anything its GPU work reaches, through commands, addresses or bindless slots, and hands it to `FrameSlot::begin(epoch)`; the slot completes it once the frame's fence signalled (at its next `begin` or drop), or right away if the frame failed before it was submitted. Core reserves it in the render sub-app's `extract`, before `ExtractSchedule` (`FrameEpoch`, taken by `render`), and the headless renderer before its extract. Dropping an image, buffer, semaphore, swapchain, surface or acceleration structure queues its destructor stamped with `epoch::latest()`; destructors run in drop order once every epoch up to their stamp completed, never right away, so replaced resources are just dropped. What a present may use (semaphores, swapchains, surfaces) waits for one epoch more, since a present has no fence. `lava::wait_idle` completes every submitted epoch and runs what that frees (call it outside `Frame::execute`: destroying an image locks the queues' pending accesses). Slots the GPU reads by index follow the same rule by hand: core's material free list stamps a freed slot with `epoch::latest()` and reuses it once `epoch::completed()` reached that.
- Ray tracing (`vkobjects/acceleration_structure.rs`, `vkobjects/rt_pipeline.rs`): three features, `acceleration_structure`, and `ray_query` and `ray_tracing_pipeline` on top of it (each only where the device has it; a pass whose SPIR-V uses ray queries, `PassEntry.ray_query`, or a ray tracing pass gets no module or pipeline without its feature and panics when recorded). `Blas`/`Tlas` (`AccelerationStructure<Bottom/Top>`) own their memory (`create_acceleration_structure2` from an address range) and know their device address (not their buffer's) and scratch sizes (multiples of `scratch_alignment()`, so one scratch slice serves a batch). A BLAS is built from `BlasGeometry::Triangles` (`Triangles::new`/`indexed`, any `VertexPosition`, u16/u32 indices, optional transform, `opaque`) or `::Aabbs`, a TLAS from `Instances` of `Instance` (lava's mirror of `VkAccelerationStructureInstanceKHR`, which passes can write too). `cmd.build`/`cmd.update` (refit, `BuildFlags::allow_update`) record one `vkCmdBuildAccelerationStructuresKHR` per call; compaction is `cmd.query_compacted_sizes` into a `QueryPool<CompactedSize>` (polled on the host, never waits), `compacted(size)` and `cmd.compact`. Barriers: a structure's memory is its buffer's range, and every acceleration structure command runs at the build stage; a TLAS build or a trace also reads `EVERY_ACCELERATION_STRUCTURE` (the BLASes lava can't list), an empty range that only conflicts with acceleration structure writes. Trace reads add `MEMORY_READ`, because Mesa's ANV otherwise lets a trace after an in-submission rebuild see stale nodes (`TRACE_READ`). `cmd.raytrace(bindings, [w, h, d])`/`raytrace_indirect` dispatch ray tracing passes.
- Queries (`lava/src/query/`): a `QueryPool<K>` is `count` queries of one sealed kind: `Timestamp` (`cmd.write_timestamp(&pool, i, stage)`; `elapsed_ns` handles the clock's valid bits, `instant` calibrates with `VK_KHR_calibrated_timestamps`), `PipelineStatistics` (flags chosen at creation, `PipelineStats::get(flag)`), `Occlusion` (`RasterBuilder::count_samples(&pool, i)` after a draw; exact counts need `Features::precise_occlusion`), `Performance` (hardware counters from `query::counters()`: at most `MAX_COUNTERS`, one counter pass, graphics family; the pool holds the profiling lock until it is destroyed) and `CompactedSize`. `cmd.query(&pool, i, |cmd| ..)` wraps commands in a statistics, occlusion or performance query, one active per kind. A pool holds one recording: the first command of a recording that touches it resets it on the host and panics if an earlier frame that recorded into it hasn't completed (`epoch::completed()`), so keep one per frame in flight. Pools are created reset, `read(first, &mut out)` never waits (false until the recording finished), and dropping one waits for its frames (Epochs). Scope observers (`query/observer.rs`) are lava's hook into recordings, like a tracing subscriber's `on_enter`/`on_exit`: `cmd.measure(Some(&mut observer), name, f)` attaches a `ScopeObserver` while `f` records, and it sees the root `name`, every `cmd.scope(name, f)` (also a debug label; there is no unbalanced begin/end) and every pass and rendering (`ScopeInfo { name, depth, pass }`), each entered and exited once in nesting order. Its hooks get a `QueryRecorder`, which can only write timestamps and begin and end queries (`is_active::<K>()` says whether one of that kind is open, e.g. a `cmd.query` around the scope), so what `on_enter` records comes before the scope's commands (a pass's barriers included) and what `on_exit` records after them. `measure` holds the observer as a lifetime-erased pointer and clears it also when `f` panics (`catch_unwind`, then `resume_unwind`). Frame slots know nothing about queries.
- `lava-tests` (`publish = false`): lava's GPU tests as an ordinary lava user, with their own passes (see Tests).
- The engine (`../GameEngine`, its own `CLAUDE.md`) is lava's main user: `core/build.rs` compiles its passes with lava-build-slang, `core` records them. Check that it still builds after changing lava's API.

## Bindless slots
- Lava never picks a descriptor index: `Image::new`/`with_mip_levels`/`with_params` make an unbound image (null `handle`), and the builder calls `bind_sampled(index)`/`bind_storage(index)` (gated by `IsSampled`/`IsStorage`) bind it right away and return it, e.g. `Image::new(extent)?.bind_sampled(a).bind_storage(b)` for an image in both sets. Both go through `bindless::bind(images, handles)`, which writes each image view into the slots of the handle at the same position (`BindlessHandle::sampled(i)`/`storage(i)` name one set), checks the usage, and makes one `vkUpdateDescriptorSets`; it sets no handle on the image. A `Swapchain` never binds its images, also not after `recreate`: `bind_storage(indices)` puts image `i` at the `i`-th index, and `recreate` hands back the old swapchain, whose semaphores and slots are released once the frames and presents that may use them are done (Epochs). Both sets are `UPDATE_UNUSED_WHILE_PENDING`; dropping an image leaves its descriptor stale.
- `lava::bindless::on_drop(hook)` sets a global function called with every bound handle whose view is destroyed: each handle of a destroyed `Image` that isn't null (the whole view's, then each mip's) and of a destroyed `Swapchain`'s images, once every frame that may reach it is done (Epochs). The engine's slot allocator refills its free lists from it.

## Shader pipeline
- `core/build.rs` calls `lava_build_slang::Shaders::new().passes(dir).include(dir).define(name, value).optimization(..).compile()` (paths relative to the package, canonicalised). lava-build-slang compiles each pass with `shader-slang` (one session per pass, `lava-build-slang/src/compile.rs`, which its hot reload shares, so both compile alike), writes SPIR-V to `$OUT_DIR/lava/passes/`, and reflects the `[[vk::push_constant]]` struct and the specialization constants (`lava-build-slang/src/codegen.rs`) to **generate `$OUT_DIR/lava/bindings.rs`**, rewritten only when it changed. `core/src/bindings.rs` includes it with `lava::include_passes!()`, so the passes are `crate::bindings::*` in core, and `crate::bindings::PASS_MAP` (every `PassEntry`, the SPIR-V always embedded with `include_bytes!`; nothing lava doesn't read) goes to `lava::init`, which lava can't include itself since it is compiled before the application's build script runs. The generated code needs `glam` and `bytemuck` (with `derive`) in the application, derives only `Pod`, `Zeroable`, `Copy`, `Clone` and `Debug` (the application implements anything else, like core's `Default` impls in `bindings.rs`), uses only lava's public API (`BindingOutput::new`/`with_constants`, `BufferSlice::access`/`address`, `ImageView::access`, `Tlas::trace_accesses`: the API for other binding generators, e.g. GLSL). For example, `raster_ui.slang` → `RasterUi::push_bindings(...).constant_bindings(...)` returns a `Bindings<kind::RasterVertex, ..>` that you borrow into `cmd.raster(extent, [Attachment::color(view, None)]).draw_indexed(&ui, ...).record(name)` (a compute pass's goes to `cmd.compute()`). A pass's push constants are at most `MAX_PUSH_CONSTANTS_SIZE` (256, `pipeline.rs`) bytes, the range of the shared pipeline layout (lava-build-slang rejects a bigger struct); its specialization constants have no limit. The generated return types spell out each section's size, so a binding has no inline capacity and never allocates; the pipeline arrays are sized at init from the map.
- Matrices use column-major layout (`matrix_layout_column` in lava-build-slang's `compile.rs`, shared by the build and hot reload), so a glam `Mat4` arrives untransposed and shaders write `mul(M, v)`.
- Push-constant field types map like this: `Buf<T>`/`MutBuf<T>` → `BufferSlice<T, U: IsStorage>`, a raw pointer `T*` → a `u64` address without an access (the shader clocks' `Clocks`), and `Img` → `ImageView` (bindless handle, its format bounded by `HasTexels<[T; N]>` of the shader's element type): `Tex2D` reads through the sampler (`IsSampled`), `Image2D`/`MutImage2D` through the storage descriptor (`IsStorage`), and `MutTex2D` reads through the sampler but writes as storage (`UnifiedBinding`, an image bound in both sets). A typed load of a storage image costs several times a sampler fetch on Intel (it was a quarter of the tonemap, now the composite pass), so read an image through the sampler whenever its usage allows. Inside structs behind a `Buf`, `Img` and `DynImg` fields become a `BindlessHandle`. `Accel` (a TLAS's address, `accel.get()` is the `RaytracingAccelerationStructure`) → `&Tlas`, a `u64` inside structs (register it with `BindingOutput::acceleration_structure_read`), never an `SCONST`. Slang structs that mirror a lava type (`MIRRORED_TYPES` in `codegen.rs`: `AccelerationStructureInstance` → `Instance`, whose fields are public for the checks) aren't generated, only layout-checked. `Img` and `DynImg` have `GetDimensions()`. `DynImg` (`bindless.slang`) reads whichever of the sampled/storage index isn't `NULL_HANDLE`; the UI pass uses it for `UIVertex.texture`, and images referenced this way get no automatic barrier: declare them with `cmd.record_access`. Slang numbers fragment outputs from location 0 whatever their `SV_Target` index, so a pass that writes attachments other than the first gives them `[[vk::location(n)]]`. Every pass is its own SPIR-V module, so passes can share entry points from an include (the scene passes' `scene_mesh`). A generated push-constant struct gets Slang's alignment (`repr(C, align)`), so its tail padding matches.
- A ray tracing pass (`ray_tracing.slang` in lava-build-slang's `slang/`) has one raygen and any number of miss, hit (closest hit, any hit, intersection; procedural with an intersection shader) and callable entry points; `[Group(n)]` puts one at index n of its binding table region (the miss index, an instance's `sbt_offset`, the callable index; 0 without it, dense per region; hit entry points with the same index form one group), `[MaxRecursion(n)]` on the raygen sets the trace depth (1 without it). `compile::ray_tracing_groups` checks them, the pass table bakes them, and `layout_hash` covers them, so a hot reload that regroups is refused. Binding table records hold only handles, no shader record data.
- Specialization constants are baked into the pipeline, for values that are the same on every run (sizes, modes, device limits, a bindless handle that is fixed for the app's lifetime, like the font atlas's). Never put buffer addresses in them: an address differs from run to run, so Mesa's shader cache never hits and every start compiles the pipelines again (0.7 to 1.2 s here, against 0.1 ms cached), while the baked addresses gained nothing measurable. Declare them with `SCONST(T, name)` (`bindless.slang`; any 8-byte handle type: `Img` aliases, `DynImg`, also `Buf`/`MutBuf`, which lava's test uses) or a plain `[SpecializationConstant] const uint name = 0;`. They become the parameters of the generated `constant_bindings`, in id order, with the same accesses and barriers as push constants. A pass with them keeps its pipelines in a map keyed by the constant bytes (laid out by `PassEntry.constants`; raster pipelines are keyed by raster state first; a key is copied to the heap only when its pipeline is made, a lookup takes the binding's bytes), so every new value builds a pipeline at first use, and a pass reaching 16 pipelines logs a warning: pass values that change on resize or per frame (frame-slot offsets, attachments, settings) as push constants.
- Runtime hot reload is a debugging aid behind the `hot-reload` cargo feature of `core` and `game` (default on), which makes core depend on `lava-build-slang` with its `hot-reload` feature, so keep it simple rather than fast. The build script also writes `$OUT_DIR/lava/hot_reload.rs`, a `hot_reload::Build` (search paths, defines, optimization, watched directories, and per pass in map order its source and layout hash), which lava never sees. `lava_build_slang::watch!()`, which core calls right after `lava::init` (windowed and headless), includes it from the calling crate's `OUT_DIR`, watches its `watch_dirs` (the pass and include directories the build script was given) and lava-build-slang's `slang/`, and recompiles changed passes (a pass's `source` is its absolute path; any other changed file reloads every pass) with the same options on its own thread, then hands the SPIR-V to `lava::pipeline::reload_pass(index, spirv)`, which replaces the pass's module and pipelines in the `PipelineManager` (`lava/src/pipeline.rs`, the pass table types and every pass's pipeline cache) right away. There is one `PipelineManager`, which hands out raw `vk::Pipeline`s (a ray tracing pass's `RaytracingPipeline` with its binding table is lent to a closure); a reload swaps the new pipelines into its caches and retires the old ones, which are destroyed once no frame can use them (Epochs). Without the feature nothing watches and nothing is ever replaced. Changing a push-constant or specialization-constant layout (or the entry points) still needs `cargo build` so the bindings get regenerated: `BuiltPass.layout` hashes them (`compile::layout_hash`) and a reload whose hash differs is refused with an error, as is one the driver rejects (nothing is replaced then); reloading rebuilds every cached specialization.

## Tests (lava, lava-macros, lava-build-slang, lava-tests)
- `cargo test -p lava -p lava-macros -p lava-build-slang -p lava-tests`. Add `-p lava-build-slang --features hot-reload` for the hot reload's watcher tests. Narrow with `-p lava --lib` (pure unit tests, no GPU), `-p lava-build-slang` (the compile helpers, plus the watcher with `--features hot-reload`), `-p lava-tests --lib` (the generated pass map), `-p lava-tests --test gpu_headless` (real GPU, headless, validation layer on, any validation error fails the test), `--test gpu_ray_tracing` (acceleration structures, ray queries and pipelines on a small scene, `lava-tests/shaders/include/ray_scene.slang`; skips without the features), or `--test gpu_window` (surface/swapchain/present; own `main`, opens a window briefly, skips without a display).
- Pure logic is tested in `#[cfg(test)] mod tests` at the bottom of each module. Never construct a `Buffer`/`Image` or call `Ctx::*` there: `Ctx::get()` blocks forever when lava isn't initialised.
- GPU tests share one context through `lava-tests/tests/common` (`gpu()` guard serialises tests and checks validation errors), so they can reuse the same bindless indices (0, 1, …).
- **Lava's tests never use engine passes.** They live in `lava-tests`, an ordinary lava user: its `build.rs` compiles `lava-tests/shaders/*.slang` with lava-build-slang, and the tests import `lava_tests::bindings::*` and pass its `PASS_MAP` to `lava::init`. The generated bindings' tests (push constants, accesses) are in `gpu_headless.rs`, since slices and views need real buffers and images.
- `lava-tests/benches/recording.rs` (`cargo bench -p lava-tests --bench recording`, headless, validation off) times recording the test passes into real command buffers. Compare ratios between variants or alternating runs of two builds (`taskset -c 2`), not absolute times, which move with the CPU clock.
- Golden images live in `lava-tests/tests/golden/*.png`. A mismatch writes `<name>.actual.png`/`.diff.png` to `target/tmp/golden-failures/`. After an intended change to a test shader, re-bless with `LAVA_BLESS=1 cargo test -p lava-tests --test gpu_headless` and look at the PNGs.
- Slang gives shaders D3D-style `SV_VertexID`/`SV_InstanceID` (without `first_vertex`/`first_instance`).

## Commands
- lava builds on stable Rust (Arch's `/usr/bin/cargo` or rustup's), edition 2024, with no `#![feature]`s; keep it that way.
- **Forks.** `ash`, `ash-window`, `gpu-allocator` and `shader-slang` are lava's own forks, published as `lava-ash`, `lava-ash-window`, `lava-gpu-allocator`, `lava-slang` and `lava-slang-sys` (lib names unchanged, so the code says `ash::`, `shader_slang::`), from `github.com/DerEchteKarsten/{ash,gpu-allocator,slang-rs}`, branch `lava`, checked out at `../forks/`. The workspace `Cargo.toml` names each with `package =`, a version (what gets published) and a path (what builds here). ash is upstream master (`VK_KHR_device_address_commands`; master renamed `push_next` to `push`, a `vk::TaggedStructure` method, and extension loaders from `new` to `load`), gpu-allocator its `ash-next` branch on lava-ash. Fix problems in a dependency in its fork rather than working around them here; bump ash and gpu-allocator together.
- The Slang SDK lives in `slang-sdk/` (gitignored; `SLANG_DIR` in `.cargo/config.toml`; the engine's config points at it too). lava-slang-sys doesn't link Slang: it loads `slang-compiler` at runtime from the path its build script found in `SLANG_LIB_DIR`, `SLANG_DIR` or `VULKAN_SDK` (else by name from the system loader), so nothing needs an rpath or `LD_LIBRARY_PATH`. Its bindings are pregenerated; `--features shader-slang/bindgen` regenerates them (needs clang).

## Don't read
`target/`, `slang-sdk/`, `*.spv`, `Cargo.lock`. These are binary, generated, or huge, and the project settings deny them.
