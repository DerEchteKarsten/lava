# lava

Vulkan abstraction in Rust (stable, edition 2024) with bindless resources, automatic barrier tracking and typed pass bindings generated from Slang at build time. Its main user is the game engine in `../GameEngine` (`core` depends on `lava` and `lava-build-slang` by path); its docs show how the engine uses lava where that explains a design.

## Orientation: read this before exploring
- A **code map** (each file's purpose, key types, plus live git state) is injected at session start by a `SessionStart` hook, which runs the engine's `tools` generator (`../GameEngine/tools`) with `--root .`. Check it before running `ls`/`rg`.
- Full pub signatures and struct fields live in `.claude/context/api/{lava,lava-build-slang,lava-tests,lava-macros}.md` (`lava-tests.md` also lists the generated test pass bindings, from the newest debug build). Read the relevant file instead of grepping for an API.
- To refresh them by hand: `cargo run -q --release --manifest-path ../GameEngine/tools/Cargo.toml --target-dir ../GameEngine/target/tools -- --root .` (stable cargo, cached by mtime). The engine's own sessions map lava too (`--with ../lava`).
- **Subagents don't get the hook output.** When delegating exploration, tell the subagent to read `.claude/context/codemap.md` first.
- Known bugs, intended limitations and ideas for future work are listed in `STATE.md`; the publishing review is `lava/SURVEY.md`. Check them before debugging or designing, delete an entry when you fix or build it, and add bugs you find but don't fix and ideas worth keeping.
- Every `.rs` file starts with a one-line `//!` doc that feeds the code map. Keep it accurate when a module's role changes, and add one to every new file.

## Crates (dependency order)
- `lava-macros`: proc macros for lava (validation tracing).
- `lava-build-slang`: lava's Slang frontend, called from an application's `build.rs` (see Shader pipeline); compiles its Slang passes and generates their bindings and `PASS_MAP`. Its `slang/` (searched by every session) holds `bindless.slang` and `ray_tracing.slang`, the Slang side of lava's shader contract (the "Shader contract" section of lava's `lib.rs` docs: the set and binding declarations lava maps to its descriptor heaps, push data, handle, sampler and instance layouts), and `profile.slang`, shader clock helpers lava has no part in, whose readout it generates (see Shader clock regions). With its `hot-reload` feature (only as a normal dependency; the build script's copy never compiles lava) it also holds the runtime shader hot reload. The only crate that links Slang; lava has no Slang in any feature combination, so a frontend for another language (`lava-build-glsl`, see STATE.md) could sit beside it.
- `lava`: Vulkan abstraction over `ash` + `gpu-allocator`; it takes SPIR-V and has no Slang. Global `Ctx` state, bindless descriptors in two `VK_EXT_descriptor_heap` heaps, which shaders index directly (`ImageHandle<K>`, and runtime `Sampler`s; lava allocates the slots, see Bindless slots), `lava::init(&Config { display, validation, disabled, pipeline_cache, ..Config::new(&PASS_MAP) })` (`display: None` = headless; the application's pass map, see Shader pipeline; `app_name`/`app_version` for `VkApplicationInfo`; `validation` in any build, a warning and no validation without the layer installed; the optional features lava leaves off even where the device has them, for tests; an optional `&'static Path` of the `VkPipelineCache` data, see Pipelines; `memory_blocks`, the allocator's block sizes (`memory_report()` reads its live bytes, counted at every allocation and free, `ALLOCATED`, and its blocks' capacity, plus the cached heaps and the budget); there are no init-time samplers; see Lifecycle and errors). Device features live in `features.rs` (see Optional features): lava tries the GPUs by type (`state::device_order`: discrete, integrated, then virtual and CPU ones such as lavapipe, with a warning) and picks the first with everything lava itself needs (Vulkan 1.4, `FeatureChain::lava_missing`: descriptor heaps with 256 bytes of push data, untyped pointers (`VK_KHR_shader_untyped_pointers`, which heap-indexing SPIR-V declares; a pending write gets no second barrier for an access one earlier barrier already made it visible to (each barrier's destination stages and accesses are kept as a pair, `PendingWrite::visible`), a layout transition or acquire becomes the image's pending write at its barrier's destination stages, visible there, replacing the image's earlier accesses (`PendingAccesses::made_visible`), pending buffer and image reads are dropped once their submission completed, and once there are more than 64 pending buffer writes the completed ones fold into one write of every address (`EVERY_BUFFER`) that keeps the visibility all of them had; A generated `Pass::push_bindings(...)` returns a `Bindings<'a, K, P, I, B, C>` (a pass with specialization constants returns an `IncompletePass` that `.constant_bindings(...)` completes; the zero-sized `kind::{Compute, RayTracing, RasterVertex, RasterMesh}` marker decides where it can be recorded), sized by what the pass has: `P` bytes of push constants, `I` image and `B` buffer accesses (lava's `ImageUse`/`BufferAccess`), `C` bytes of specialization constants. It derefs to the unsized `BindingOutput<K>`, one run of bytes (header, push constants, image accesses, buffer accesses, constants) that commands borrow, so a call site writes `cmd.compute(&Pass::push_bindings(..), ..)` and can record one binding twice. A resource a pass reaches without naming it (through a handle or pointer in a buffer) is passed to the command with its bindings, as the last parameter of `compute`, `compute_indirect`, `raytrace`, `raytrace_indirect` and every `Draw` constructor: `Option<Accesses>`, two slices made with `ImageUse::{sampled_read, storage_read, storage_write}(view)` and `BufferAccess::{read, write}(slice)` (`BufferAccess::trace(&tlas)` gives a trace's two accesses); the command sets their stage to its pass's (`PassKind::stages`, the `kind` markers' `STAGES`, which generated bindings use too) and tracks them like its bindings', and an attachment a draw reaches this way is rendered in `GENERAL`. There is no declaring ahead of a command. Index and indirect buffers are accesses of the draw or dispatch, not of the binding. A pass pushes only its own struct as push data (`vkCmdPushDataEXT`), from offset 0, padded to whole words; the rest isn't zeroed. `cmd.raster(area, [Attachment::color(view, clear), ..])` starts one rendering of `area` (a `Rect`, an offset and an extent, also the type of viewports and scissors; a `UVec2` is that extent at the origin) with its color attachments (lava sets no maximum of its own; the device's `maxColorAttachments` applies; each is cleared or loaded, and stored, unless `.discard_before()`/`.discard_after()` make the load or store `DONT_CARE`, and `discard_depth_before()`/`discard_depth_after()` do the same for the depth-stencil attachment), then `depth_attachment(view, clear)` (a combined format's stencil too) or `stencil_attachment(view, clear)` (`S8Uint`, or a combined format's stencil alone; one depth-stencil image per rendering, a later call replaces it), `viewport(rect)`/`scissor(rect)` (its draws' defaults, else the area), `layers(n)` (layered: the vertex or mesh shader picks each primitive's layer, `SV_RenderTargetArrayIndex`, which vertex shaders declare with `shader-output-layer`) or `view_mask(mask)` (multiview, `SV_ViewID`, part of the pipeline key; direct draws take `.first_vertex(n)`, `.first_instance(n)`, `.vertex_offset(n)`, which panic on draws they don't fit; `multi`/`multi_indexed` (`VK_EXT_multi_draw`, `multi-draw`) return `Gated` draws; indirect commands are a slice of any `T: StartsWith<C>`, an `unsafe` marker trait for types that start with the command `C` (each command type implements it for itself), `size_of::<T>()` apart, and `compute_indirect`/`raytrace_indirect` take one the same way and read its first command), each draw with its own `RasterState<COLOR_ATTACHMENTS>` (`command_buffer/raster_state.rs`: topology, cull mode, front face, polygon mode, line width/mode/stipple, provoking vertex, conservative raster, depth test/write/bounds/bias/clamp/clip (`depth_clip` unset: clipped unless clamped, on every device), stencil, logic op, blend constants, an optional viewport and scissor of its own (set only when they change), and per colour attachment a `Blend::{Replace, Alpha, Add, Attenuate, Skip, Equation(..)}` (`blend(b)` for all, `blends([..])` with `independent-blend`; setters of state that needs a feature are `#[cfg]`'d by it and return `Gated` states; `Draw` constructors panic for values the device can't draw (`RasterState::check`: `SRC1_*` factors without `dual-src-blend` or beyond `maxFragmentDualSrcAttachments`, a stipple factor outside 1 to 256, widths outside `lineWidthRange`, depth bounds and clamp ranges outside 0 to 1, underestimation without `primitiveUnderestimation`, primitive restart of lists, empty viewports, scissors outside 2^31), and `record` for blending into a format without `COLOR_ATTACHMENT_BLEND` (`Ctx::format_features`, cached per format)), and `record(name)` records them in one rendering under one GPU scope. Core 1.3 state is always dynamic (stencil state as one `FRONT_AND_BACK` call where both faces are alike); the extended dynamic state of the `dynamic-*` features (`Dynamic::of`, computed once at init, `Ctx::dynamic()`) is dynamic where the device has it, and elsewhere baked: a raster pipeline is keyed by its attachment formats, view mask, specialization constants and the draw state the device can't set dynamically (`RasterKey`/`RasterKeyRef` with `Baked` and, without `assert-dynamic-blend`, the blends and write masks; `Baked` also holds a vertex pipeline's topology class (`topology_class`) unless the device has `dynamicPrimitiveTopologyUnrestricted` on an enabled `VK_EXT_extended_dynamic_state3` (`Dynamic::topology_unrestricted`), so a dynamic topology never leaves the baked class; its other fields exist only where their capability is compiled and their dynamic state isn't asserted, the `bake_*` cfgs of `lava/build.rs`, and hold the draw's value only where the device lacks the dynamic state, so draws share pipelines where it has it), looked up without copying through hashbrown's `Equivalent`; `create_raster_pipeline` fills the static create infos from the key; a rendering sets every dynamic state at its first draw and then per draw only what changed, and binds a pipeline whenever the key changes. Within a rendering, depth and blending follow draw order without barriers, but nothing else does, so `record` panics when a draw accesses what another draw of it writes (attachments aside, and pairs of `BufferAccess::unordered()` accesses: atomics or disjoint writes whose order the application guarantees doesn't matter). Attachments are views of one mip, covering the render area. `RasterBuilder<'a, N>` has the attachment count in its type, and so does a `Draw<'a, N, E>` (`E`: its index or indirect buffers), so a draw with the wrong number of blends doesn't compile; a `Draw` derefs to the unsized `DrawOutput` (blends, write masks and those buffers as sections, like `BindingOutput`), which the builder borrows: its methods take and return `&mut Self`, the first 16 draws are kept inline (a `SmallVec` of pointers in the builder, tied to `'a` by a `PhantomData<&'a DrawOutput<'a>>`, so draws can be temporaries of the recording statement, dropped before the builder made first: a `SmallVec` of references would need them alive at its `Drop`, and `#[may_dangle]` is nightly-only), and draws added in a loop are built before the rendering. Direct draws of 0 instances are skipped. Raster passes without a fragment entry point (`PassKind::RasterVertex`/`RasterMesh` with `fragment: None`) draw depth and stencil alone. Dynamic rendering local read isn't supported (STATE.md).
- Unsized types with sized builders (`Bindings`/`BindingOutput`, `Draw`/`DrawOutput`) are declared with the crate-internal `unsized_struct!` (`lava/src/unsized_struct.rs`): fixed fields, then the section lengths, then `[T; L]` sections (aligned to at most 8) that the unsized struct reads back as slices. Use it for any new one.
- Traits only lava implements (`Format`, `ImageUsage`, `BufferUsage`, `Dim`, `Views`, the aspect markers, the image kinds of `image/kind.rs`, `QueueKind` with `HasCompute`/`HasGraphics`, the query kinds, `Level`, `IndexFormat`) have the supertrait `crate::sealed::Sealed`, a public trait in a private module: other crates can bound by them but not implement them, and their sub-traits (`IsSampled`, `HasTexels`, ...) are sealed through them. Seal new ones the same way; `VertexPosition` stays open for vertex types of other crates.
- Submission and presenting (`queue/`, `present.rs`): a `Timeline<K>` (`Timeline::new(in_flight, staging)?`, the staging ring size in bytes, see uploads; `K` is `queue::Graphics`, or `Compute`/`Transfer`, which need `async-compute`/`async-transfer` and return `MissingFeature` without a dedicated family; at most `MAX_TIMELINES` = 8, else `Error::OutOfTimelines`) owns one of 8 timeline semaphores (`queue/timeline.rs`, `INDICES`, kept for lava's lifetime, so values go on and old `Wait`s stay valid when another timeline gets the index), pinned to the least shared queue of its family (`DeviceQueues`/`FamilyQueues` in `queue/mod.rs`: graphics plus the dedicated compute and transfer families, at most 8 queues each, a `Mutex<vk::Queue>` per queue and one `Mutex` of per-queue timeline counts per family; `Ctx::queue_family(Kind)`/`queue_count(Kind)`), with `in_flight` command pools. Each index has two counters: the stamp (`timeline.reserve()` counts it up without waiting, before a frame reads anything its GPU work reaches; core does it in `extract`) and the value its last submission signalled. `timeline.begin()?` borrows the timeline mutably (`Submission<'_, K>`, so one at a time, without a runtime check; core's `render()` holds its `FrameTimeline` through `world.resource_scope`) and waits for the frame slot's last submission and raises the stamp to at least the next value; `submission.slot()` cycles through the slots for per-frame rings and query pools; `submission.wait_for(other.at(GraphicsStage::Raster))` adds waits at a stage of the waiting family's set (`Wait<S: StageSet = AllStages>`; `QueueKind::Stage` is `GraphicsStage`, `ComputeStage` or `TransferStage`, and `wait_for` takes a `Wait<S: StageOf<K>>`: `AllStages`, its own set, transfer stages everywhere, compute stages on graphics, so a raster stage on a compute submission doesn't compile; ray tracing stages are masked to the indirect reads without ray tracing pipelines; one on its own timeline is dropped, two on one timeline keep the later value at both stages); `submission.submit(|cmd: &mut CommandBuffer<K>| ..)? -> Wait` signals the stamp, so a skipped frame just leaves the stamp ahead until the next submission catches up (`wait.block()`/`block_timeout(d) -> bool`/`is_done()`, `Wait::all(&[..])`/`all_timeout`, one `vkWaitSemaphores`). A value no submission will signal is signalled from the host (`host_signal`, after the index's earlier submissions): a timeline dropped with its stamp ahead (`reserve()`, an unsubmitted `begin()`), and a failed recording whose barrier-only replay failed too; device loss leaves the values alone. Polls and waits return `Result`, so `Error::DeviceLost` comes out of `begin`, `submit`, `block`, `wait_idle` (logged once, `Ctx::device_lost`). `submit` records with the timeline's pending accesses borrowed (`Recording<'p>`, `CommandBuffer<'p, K>`), first the queued bindless rewrites, then the closure (uploads only where it calls `cmd.drain_uploads`), ends every submission with a barrier that makes its writes host-visible (readbacks, clock counters), and submits with the waits and signals; a recording that never reaches the GPU (its closure panicked, or recording or submitting failed) is replaced by a submission of just the barriers it computed (`Recording::barrier_log`) with the same waits, signalling the value, so the tracked image states stay true, its drained uploads are published again, and the panic continues (a submission that used an acquired swapchain image without presenting it, or whose recording left a query active, panics with that message after the replay). `CommandBuffer<K>` wraps the untyped `Recording`: renderings, blits and presents need `K: HasGraphics`; dispatches, traces, acceleration structure commands and image clears `K: HasCompute`; copies, fills, updates, timestamps, scopes and `flush_all` work on every kind, and queries of the kinds its family records (`query::RecordedOn<K>`, see Queries) (a transfer family binds no descriptors; its image copies need 4-byte aligned buffer addresses and boxes within its `minImageTransferGranularity`, and copies into depth or stencil images need graphics). Images are `EXCLUSIVE` to one family at a time, tracked as the owner in their state: an access by another family panics unless the owner recorded `cmd.release::<D>(view)` (or `record_uploads` of a batch for `D` released it), and the receiver's first access records the acquire half in a barrier call of its own (`Barriers.acquires`). The receiving submission must `wait_for` the releasing one, which lava doesn't check. The image's states are the image's (one, or one per mip indexed by mip level, also in a mip view), so a release forgets the image's pending accesses only once the family owns none of its mips (`released_by`). Buffers are `CONCURRENT` between every family lava created queues of. Host image copies (`Image::copy_from`) aren't synchronised with submissions in flight. `PresentSurface<U>` (`present.rs`) owns a window's surface, its swapchain (made by the first `acquire`, recreated there on a new size, present mode or composite alpha or a suboptimal or out-of-date result, up to three tries; the old one moves to the surface's retired list before the new one is created, so a failed creation leaves none and the next starts with a null `oldSwapchain`), the semaphores and present fences between them, and one current image. `new(display, window, &[SurfaceFormat])` needs `present-fences` (`MissingFeature` without it) and picks the first preferred `SurfaceFormat { format: format::Dynamic, color_space: ColorSpace }` the surface has whose format supports `U`, else another one lava has a type for, logged, with `is_preferred_format()` false (`surface_format()`, `format()`, `color_space()`); colour spaces besides sRGB, HDR10 among them, come from `VK_EXT_swapchain_colorspace`, which init enables with a display where the instance has it. `PresentMode` is an enum (`Fifo`, `FifoRelaxed`, `Mailbox`, `Immediate`, and `FifoLatestReady` with `fifo-latest-ready`): `present_modes()`, `supports(mode)`, `set_present_mode(mode) -> bool`; `set_composite_alpha(CompositeAlpha) -> bool` (default: the first of `CompositeAlpha::ALL` the surface supports); `set_hdr_metadata(&HdrMetadata)` (`hdr-metadata`) applies to the swapchain and every later one. Surface capabilities are cached per requested size and queried again on a new size, a suboptimal or out-of-date result and after a recreation. `surface.acquire(window_size)? -> bool` makes an image current (`false` at zero size or minimised) with its state reset to `UNDEFINED` (its contents are discarded), `surface.current_image()` is its view for the submission, which ends with `cmd.present(&mut surface)` (the image's last command in the recording: a later access panics; panics if a submission presented it already; it marks the image presented last, after its barrier), then `surface.present()?` or `present::present_all(&mut [&mut a, &mut b])?` (one `vkQueuePresentKHR` for several surfaces, of any usage) presents it on graphics queue 0. `acquire`, `present` and `present_all` panic on a thread that is recording (`lifetime::RECORDING`): call them before or after `submit`. `present` takes its fence (a free one reset, or a new one) before the image stops being current. An image no submission presented stays current: `present()` leaves it, the next `acquire` returns it again, at its size, with its tracked state reset (only a failed recording can have touched it), so a resize takes effect a frame later; an `acquire` after a presenting submission without `present()` presents first. Only dropping the surface with a current image waits for an empty submission that consumes the semaphore it left signalled. The presenting submission must be the one that first uses the image (else it panics): it waits for the acquire at the stage of that first access (the image state's `acquired` flag) and signals the image's own present semaphore, and `cmd.present` writes the recording's timeline and value into the surface's current image while recording, before anything is submitted. A replaced swapchain waits in the surface until its stamp is done and its present fences signalled, and the surface destroys it at an acquire; dropping the surface waits up to 1 s for its present fences, then retires everything. Swapchain images are bound in every bindless set their usage allows and owned by graphics.
- Lifetimes (`lava/src/lifetime.rs`): views, slices and `Wait`s are `Copy` and borrow or name what they use, and lava counts nothing per use. Dropping an image, buffer, view, acceleration structure, query pool, pipeline (hot reload), bindless reservation or present surface queues its destructor stamped with every timeline's stamp (`lava::latest_stamp()`, a `Stamp`); destructors run in drop order (views before their image) once every timeline completed its stamp, never right away and never on a thread that is recording (`lifetime::RECORDING`: destroying an image locks the timelines' pending accesses), so replaced resources are just dropped. Timelines are polled when a submission begins, when a `Wait` is asked, when a `Stamp` is behind its cached values (only those timelines), and by `lava::reclaim()`, which then runs what is ready (internal callers use `lifetime::run_ready`, which doesn't poll). Destructors run under one mutex (`RECLAIMING`, not `RETIRED`'s lock, since destructors retire things; a destructor that reclaims returns at once), so they run in drop order across threads. `lava::wait_idle` locks every queue, waits, polls, and runs what that frees (call it outside `Submission::submit`); `lava::shutdown` runs everything left. Slots the GPU reads by index follow the same rule by hand (core's materials keep `(index, latest_stamp())` and reuse an index once `stamp.is_done()`).
- Ray tracing (`vkobjects/acceleration_structure.rs`, `vkobjects/rt_pipeline.rs`): three features, `acceleration-structure`, and `ray-query` and `ray-tracing-pipeline` on top of it (the modules and commands are `#[cfg]`'d by them; `Blas::new`/`Tlas::new` return `MissingFeature` where checked, and a pass whose SPIR-V declares `RayQueryKHR` or `RayTracingKHR` has `Gated` bindings, like any pass whose capabilities need a feature). `Blas`/`Tlas` (`AccelerationStructure<Bottom/Top>`) own their memory (`create_acceleration_structure2` from an address range) and know their device address (not their buffer's) and scratch sizes (multiples of `scratch_alignment()`, so one scratch slice serves a batch). A BLAS is built from `BlasGeometry::Triangles` (`Triangles::new`/`indexed`, any `VertexPosition`, u16/u32 indices, optional transform, `opaque`) or `::Aabbs`, a TLAS from `Instances` of `Instance` (`unsafe Instances::new`: lava doesn't keep the BLASes it names alive) (lava's mirror of `VkAccelerationStructureInstanceKHR`, which passes can write too). `cmd.build`/`cmd.update` (refit, `BuildFlags::allow_update`) record one `vkCmdBuildAccelerationStructuresKHR` per call; compaction is `cmd.query_compacted_sizes` into a `QueryPool<CompactedSize>` (polled on the host, never waits), `compacted(size)` and `cmd.compact`. Barriers: a structure's memory is its buffer's range, and every acceleration structure command runs at the build stage; a TLAS build or a trace also reads `EVERY_ACCELERATION_STRUCTURE` (the BLASes lava can't list), an empty range that only conflicts with acceleration structure writes. Trace reads add `MEMORY_READ`, because Mesa's ANV otherwise lets a trace after an in-submission rebuild see stale nodes (`TRACE_READ`). `cmd.raytrace(bindings, [w, h, d])`/`raytrace_indirect` dispatch ray tracing passes.
- Queries (`lava/src/query/`): a `QueryPool<K>` is `count` queries of one sealed kind: `Timestamp` (`cmd.write_timestamp(&pool, i, stage)`; `elapsed_ns` handles the clock's valid bits, `instant` calibrates with `VK_KHR_calibrated_timestamps`, at most once per `CALIBRATION_PERIOD` (1 s) per pool, the best of up to four tries until the deviation, `maxDeviation` plus the host's bracket, is within `CALIBRATION_DEVIATION`), `PipelineStatistics` (flags chosen at creation, never empty (panics), `PipelineStats::get(flag)`; graphics family), `ComputeStatistics` (compute shader invocations, one `u64`, on graphics and compute families), `Occlusion` (`Draw::count_samples(&pool, i)`; `QueryPool::occlusion(count)`, or exact counts with `precise_occlusion(count)` and `precise-occlusion`), `Performance` (hardware counters from `query::counters()`, each with its `CounterUnit` and `CounterScope`: at most `MAX_COUNTERS`, lava's own cap so a query's values fit an array; graphics family; the pool holds the profiling lock until it is destroyed) and `CompactedSize`. Which kinds a family records is a type: `RecordedOn<Q>` (timestamps everywhere, occlusion, pipeline statistics and counters on `HasGraphics`, compute statistics on `HasCompute`) bounds `cmd.query` and `QueryRecorder::begin_query`/`end_query`, so the others don't compile (compile_fail doc tests on `RecordedOn`). `cmd.query(&pool, i, |cmd| ..)` wraps commands in a statistics, occlusion or performance query, one active per kind: the recording keeps the active pool and index per kind (`Recording::open_queries`), `end_query` panics unless they match, and a recording that ends with one active fails (replayed, then panics). A pool holds one recording: the first command of a recording that touches it resets it on the host and panics if the submission that recorded into it before (its timeline and value) hasn't completed, so keep one per frame slot; every timestamp, query and compacted size takes its indices through `QueryPool::take` (checked against the pool, `checked_add`), which sets a used bit per query, cleared at that reset, and panics on a second use in one recording. Counters follow their scope: `CounterScope::CommandBuffer` ones only around a whole recording, `submission.submit_profiled(&pool, i, |cmd| ..)` (begins the query as the recording's first command, before the heap binds, and ends it as its last, after the final barrier; observers see it as active), `RenderPass` ones never inside a rendering, `Command` ones anywhere; one counter pool per recording (no `performanceCounterMultipleQueryPools`). `counters::passes(selection)` and `counters::fits(selection)` (one pass, at most `MAX_COUNTERS`) say whether a selection records like any query; one of more passes only through `timeline.capture(&pool, i, |cmd| ..)` (graphics), a tool capture that records the closure once per pass, each a profiled submission with `VkPerformanceQuerySubmitInfoKHR::counterPassIndex`, blocking after each, without resetting the pool after the first pass (`Profile::pass`), so the recordings should be alike and present nothing. Pools are created reset, `read(first, &mut out)` never waits (false until the recording finished) and panics outside the pool, and dropping one waits for its submissions (lifetime). Scope observers (`query/observer.rs`) are lava's hook into recordings, like a tracing subscriber's `on_enter`/`on_exit`: `cmd.measure(Some(&mut observer), name, f)` attaches a `ScopeObserver<K>` (`K` the recording's queue kind, `Graphics` by default) while `f` records, and it sees the root `name`, every `cmd.scope(name, f)` (also a debug label; there is no unbalanced begin/end) and every pass and rendering (`ScopeInfo { name, depth, pass }`), each entered and exited once in nesting order, never inside a rendering. Its hooks get a `QueryRecorder<K>`, which can only write timestamps and begin and end queries of the kinds `K` records (`is_active::<Q>()` says whether one of that kind is open, e.g. a `cmd.query` around the scope), so what `on_enter` records comes before the scope's commands (a pass's barriers included) and what `on_exit` records after them. `measure` holds the observer as a lifetime-erased pointer to a `Typed<K>` wrapper (`observer::Observer`, the queue kind erased for the untyped `Recording`) and clears it also when `f` panics (`catch_unwind`, then `resume_unwind`). Timelines know nothing about queries besides `submit_profiled` and `capture`.
- `lava-tests` (`publish = false`): lava's GPU tests as an ordinary lava user, with their own passes (see Tests).
- The engine (`../GameEngine`, its own `CLAUDE.md`) is lava's main user: `core/build.rs` compiles its passes with lava-build-slang, `core` records them. Check that it still builds after changing lava's API.

## Optional features
- Every optional device feature is two cargo features of lava (`features!` in `features.rs`; the field of `Features` is the name with `_`, the type in `features::gate` its PascalCase): `X` compiles it and lava checks the device where it is used, `assert-X` (implies `X`) makes `init` refuse devices without it and drops the checks, neither compiles its API out (`#[cfg(feature = "X")]` on modules, types, fields and functions; internal code that runs either way asks `<gate::X as On>::on()`). `default` is every `X`; the engine turns defaults off and lists its own (`../GameEngine/core/Cargo.toml`), and so must every crate between (lava-build-slang's hot-reload dependency and lava-tests take lava without defaults).
- A function that only fails on the missing feature returns `Gated<gate::X, T>` (`T` when asserted, `Result<T, MissingFeature>` when checked; `features::gate::<F, _>(|| ..)` builds it, pairs `(A, B)` gate on both). One that fails otherwise too returns `lava::Result` and calls `gate::X::check()?` (`Error::MissingFeature`). Loaders of optional extensions are `Loader<gate::X, T>` in `Functions` (`T` when asserted, `Option<T>` when checked, read with `loaded`, only past a check). Objects that exist only past a check (a `Blas`, a host-copy image, a performance pool) need no check in their commands.
- Passes: lava-build-slang reads each pass's `OpCapability`s (`lava-build-slang/src/features.rs`, a copy of `features::SPIRV_CAPABILITIES`; its test compares them; both scans stop at the first instruction after the capabilities and extensions, lava's in place, `features::spirv_capabilities`, once per pass at init) and gates the generated `push_bindings` by them, so recording stays infallible; without the cargo feature the bindings don't compile (`#[diagnostic::on_unimplemented]` on `Feature` names it). `init` refuses a pass map with a pass whose feature lava was compiled without, and `PipelineManager` still panics when hand-made bindings of a pass the device can't run are recorded. Features map Vulkan bits one to one except where a capability allows less: `shader-int64-atomics` also enables `shaderSharedInt64Atomics`, `shader-clock` `shaderDeviceClock`, and `ray-traversal-primitive-culling` (`RayTraversalPrimitiveCullingKHR`, which ray queries imply) `rayTraversalPrimitiveCulling`, each only where the device has it (`FeatureChain::enabling` gets the queried chain); `clip-distance`, `cull-distance` and `storage-input-output-16` are their core bits; `shader-output-layer` (`ShaderLayer`, `ShaderViewportIndexLayerEXT`) is `shaderOutputLayer` with `shaderOutputViewportIndex`, `dual-src-blend` `dualSrcBlend`, `multi-draw` `VK_EXT_multi_draw`.
- `present-fences`, `hdr-metadata` and `fifo-latest-ready` exist only with a display (init clears them without one, and their `assert-` features require them only with one); `present-fences` also needs the instance extensions `VK_KHR_get_surface_capabilities2` and `VK_EXT_surface_maintenance1`, and windows need it (`PresentSurface::new`).
- `async-compute` and `async-transfer` are queue families, not Vulkan features: the device has them when it has a family with compute but no graphics, or transfer alone (`DeviceFacts`, `pick_queue_families`); lava creates their queues only where they are on, and `Timeline<Compute>`/`Timeline<Transfer>` return `MissingFeature` elsewhere.
- `Config::disabled` leaves features off on a device that has them (with what needs them, `Features::consistent`); `lava-tests/tests/gpu_missing_features.rs` uses it to test the `MissingFeature` paths and the baked draw state.
- Extended dynamic state stopped being mandatory on 2026-10-17 after vulkan.gpuinfo.org's coverage (Windows: extended dynamic state 3 72%, its conservative raster bit 56%, depth clamp control 53%, `rectangularLines` 56%; `VK_KHR_device_address_commands`, still mandatory, 15%; `VK_EXT_descriptor_heap`, mandatory since 2026-10-19, is in Mesa 26.2 and NVIDIA 610): `dynamic-*` features decide it, lava sets no sample locations, MSAA or alpha-to-one state, and `VK_EXT_color_write_enable` is gone.

## Lifecycle and errors
- Lava's globals (`Ctx`, `Functions`, `Bindless`, the `PipelineManager`, counters) are `global::Global`s: an `AtomicPtr` set by `init` and taken by `shutdown`, one load per read. What makes taking them sound (`global.rs` docs): every lava object (buffer, image, acceleration structure, query pool, sampler, slot range, surface, timeline, uploader) holds a `global::Live` count as its last field, from before its constructor touches lava until its drop finished, and every public free function that touches lava's state takes one for its call (`state::call()`); lava's own buffers (heaps, binding tables) hold uncounted ones. `shutdown` closes the count only when it is zero (one CAS), else returns `Error::ObjectsAlive { count }` and destroys nothing; `init` and `shutdown` hold `global::LIFECYCLE`. The `Ctx` box is leaked at shutdown, not freed, so getters that take no count (`Ctx::features()`, `device_properties()`, the feature checks) read valid memory while it runs; afterwards every call panics with `global::NOT_INITIALISED`. Counters of `query::counters()` are leaked too (`&'static`), and `QueryPool::performance` refuses those of an earlier context.
- `lava::shutdown()` (`#[validation_trace]`): device idle (a lost device is fine), `pipeline::save_cache_now`, every retired destructor (`lifetime::run_all`), pipelines and modules and cache (`pipeline::destroy`), the heaps (`Bindless::destroy`), the destructors that retires, the timeline semaphores (`timeline::destroy`; values go on in the next context, whose semaphores start at the index's stamp, so old `Wait`s and `Stamp`s are done), the counters, the pass map, then the allocator, device, debug messenger and instance (`Ctx::destroy`). A failed `init` runs the same `teardown` for what it made after `Ctx::init` (whose own steps undo themselves), after pure checks that need no device (`Config::disabled` naming asserted features panics; `pipeline::check_compiled`).
- Errors (`error.rs` docs): programmer errors panic (host copies of a wrong mip, region or length, `Uploader::image` likewise, sampler anisotropy out of range, performance pools of 0 queries or a bad counter count); device and environment failures are typed `#[non_exhaustive]` `Error`s: `DeviceLost`, `OutOfMemory` (Vulkan and gpu-allocator), `SurfaceOutOfDate`, `SurfaceLost`, `NoSuitableGpu { rejected }`, `Unsupported(String)`, `MissingFeature`, `OutOfBindlessSlots { heap: bindless::Heap, count }`, `OutOfTimelines`, `SliceOutOfRange`, `StagingFull`, `ObjectsAlive`, `Vulkan(vk::Result)` for the rest, `Loading`/`Allocation`/`Io` wrappers, and `Other { message, source }` only where nothing else fits (`Error::other`, and `err.context(..)`, which leaves the typed variants unwrapped). `Display` is the error's own text; only `Other` has a `source()`. No `From<String>`.
- Validation messages are `tracing` events of target `vulkan-validation` (error, warn, debug, trace by severity) with `message`, `typ` and `flags` (raw `VkDebugUtilsMessage{Type,Severity}FlagsEXT` integers, which the engine's console reads) and `validation_location`; shader printf is `info` at `lava::state`. The messenger asks for errors and only those other severities `tracing` enables at init (a subscriber installed later misses them), and the callback formats inside the event macros, so filtered messages cost nothing. `Buffer`/`Image`/`AccelerationStructure::named(name)` names the allocation (gpu-allocator's `rename_allocation`) and, with debug utils loaded (validation on), the Vulkan object.

## Bindless slots
- Descriptors live in two heaps of `VK_EXT_descriptor_heap` (`bindless.rs`), mapped `CpuToGpu` buffers with `DESCRIPTOR_HEAP` usage that every command buffer of a graphics or compute family binds once (`Bindless::bind`): the resource heap holds the image descriptors (`HeapLayout`: `count` slots, min(`MAX_IMAGE_SLOTS` = 2^16, what `maxResourceHeapSize` holds), then the implementation's reserved range), the sampler heap the samplers (at most `MAX_SAMPLERS` = 4096). Shaders index both directly (`ResourceDescriptorHeap[slot]`/`SamplerDescriptorHeap[slot]` in `bindless.slang`, `SPV_EXT_descriptor_heap` through the `spvDescriptorHeapEXT` capability of `compile::session`), so pipelines have no layout and no mappings, a heap index needs no `NonUniformResourceIndex` (heap accesses are non-uniform unless declared otherwise), and lava's slot stride must be the shader's (`OpConstantSizeOfEXT` of the descriptor type: its size aligned to its alignment, `HeapLayout::new`). Descriptors are written with `vkWriteResourceDescriptorsEXT` from a `VkImageViewCreateInfo` (`ShaderImage`, layout `GENERAL`, the depth aspect of a combined depth-stencil format) straight into the mapping; no `VkImageView` exists for them.
- An image handle is one `u32`, `ImageHandle<K>` (`#[repr(transparent)]`, `Pod`): bits 0–29 the slot of its first descriptor, bit 30 that descriptor's kind (0 sampled, 1 storage), bit 31 its width (0 one descriptor, 1 two: sampled at the slot, storage at the next); `ImageHandle::NULL` (all ones, the one invalid pattern) is the default. `K` is a sealed kind: `Sampled`, `Storage`, `Combined` (the typed kinds, `Allocatable` with their `WIDTH`), or `Dynamic` (the default, from `erase()`, for `DynImg`); `as_sampled()`/`as_storage()` (`HasSampled`/`HasStorage`) and `erase()` only retype the bits, and `sampled_slot()`/`storage_slot()` decode them, as `bindless.slang` does. Mips of a chain lie `width` slots apart (`handle.mip(level)`, `Img.Mip(level)`).
- Lava allocates the slots (one `Mutex<Ranges>` of sorted, coalesced free ranges, first fit). `Image::new`/`with_mip_levels`/`with_params` make an unbound image (null handle); `bind_sampled()`/`bind_storage()`/`bind_combined()` (`where Self: SampledImage`/`StorageImage`/both) take one or two free slots, `bind_mips_sampled/storage/combined()` one block of `mip_levels * WIDTH` (mip `i` at `first + i * WIDTH`), write right away (no submission reaches a fresh slot) and return `Result<Self>` (`Error::OutOfBindlessSlots`), e.g. `Image::new(extent)?.bind_combined()?`; a view is bound once, so a second bind panics. `Image::handle::<K>()`/`ImageView::handle::<K>()` return the handle as `K` and panic, naming the bind to call, unless the binding has `K`'s descriptors (a `Combined` binding serves all three). The slots are free again once the image is destroyed (its destructor runs once no frame reaches it, Lifetimes). A `PresentSurface` binds each swapchain image with every descriptor its usage allows (`Combined`, `Sampled` or `Storage`; a recreated swapchain at other slots; the old one frees its slots when it is destroyed).
- Slots the application indexes itself (core's textures, by asset index) come from `bindless::reserve::<K>(n)`: an owned `SlotRange<K>` of `n` handles (empty, without slots, for 0), `n * K::WIDTH` slots (`len()`, `slots()`, `handle(i)`), free again once it is dropped and retired. The public `bindless::bind(images, handles)` writes only slots of a live reservation (it panics otherwise) and sets no handle on the image. Since a frame in flight may read a reserved slot, `bind` doesn't write the heap: it queues the descriptor bytes (`Bindless::queued`, by heap offset, a later bind of the slot replacing an earlier one), and the next `submit` of a graphics or compute timeline records them before its closure (`Bindless::flush_queued`: a barrier from every earlier command of its queue, `vkCmdUpdateMemoryKHR` per run of neighbouring slots, a barrier to `RESOURCE_HEAP_READ`), so submissions before it read the old descriptor and later ones the new. Another timeline sees a rewrite only after a `Wait` on the flushing submission. A recording that never reaches the GPU queues its writes again; dropping a `SlotRange` discards its queued writes.
- Samplers are runtime objects: `Sampler::new(&SamplerDesc)` (a const builder: `SamplerDesc::new()`/`Default` is trilinear and repeating; `filter`, `address_mode`, `border_color`, `compare(op)` for `SampleCmp`, `reduction(mode)` with `sampler-minmax`, `max_anisotropy(ratio)` with `sampler-anisotropy`, checked against `maxSamplerAnisotropy`) writes a free slot of the sampler heap with `vkWriteSamplerDescriptorsEXT`, `handle()` is the `SamplerHandle` shaders take as a `Sampler`, and dropping it frees the slot once retired. Equal descriptions get separate slots.

## Shader pipeline
- `core/build.rs` calls `lava_build_slang::Shaders::new().passes(dir).include(dir).define(name, value).compile()` (`.optimization(..)` exists too; core doesn't call it) (paths relative to the package, canonicalised). lava-build-slang compiles each pass with `shader-slang` (one session per pass, `lava-build-slang/src/compile.rs`, which its hot reload shares, so both compile alike), writes SPIR-V to `$OUT_DIR/lava/passes/`, and reflects the `[[vk::push_constant]]` struct and the specialization constants (`lava-build-slang/src/codegen.rs`) to **generate `$OUT_DIR/lava/bindings.rs`**, rewritten only when it changed. `core/src/bindings.rs` includes it with `lava::include_passes!()`, so the passes are `crate::bindings::*` in core, and `crate::bindings::PASS_MAP` (every `PassEntry`: name, SPIR-V always embedded with `include_bytes!`, `PassKind` (from the entry points' stages: vertex or mesh (with task) raster passes with or without a fragment shader, compute, ray tracing) with its entry points as `&'static CStr` (`c".."` literals), constant map entries and `constants_size`; a pass's index is its position in the map, which its bindings name) goes to `lava::init`, which lava can't include itself since it is compiled before the application's build script runs. The generated code needs `glam` and `bytemuck` (with `derive`) in the application, derives only `Pod`, `Zeroable`, `Copy`, `Clone` and `Debug` (the application implements anything else, like core's `Default` impls in `bindings.rs`), uses only lava's public API (`Bindings::new`/`with_constants`, `unsafe` with the generator contract in their `# Safety` docs: the pass index and its kind marker, its push constant struct, the accesses its fields make, its constants' `constants_size` bytes; the generated calls sit in `unsafe` blocks with a `// SAFETY:` comment, and debug builds check the kind (`kind::Kind`) and constant size once lava is initialised; `BufferSlice::access`/`address`, `ImageView::access`, `Tlas::trace_accesses`, `kind::*::STAGES`: the API for other binding generators, e.g. GLSL). For example, `raster_ui.slang` → `RasterUi::push_bindings(...).constant_bindings(...)` returns a `Bindings<kind::RasterVertex, ..>` that you borrow into `cmd.raster(extent, [Attachment::color(view, None)]).draw(&Draw::indexed(&ui, ...)).record(name)` (a compute pass's goes to `cmd.compute()`). A pass's push constants are at most `MAX_PUSH_CONSTANTS_SIZE` (256, `pipeline.rs`) bytes of push data, which lava requires of the device (`maxPushDataSize`; lava-build-slang rejects a bigger struct); pipelines have no layout (`PIPELINE_CREATE_2_DESCRIPTOR_HEAP`), and shaders index the descriptor heaps directly (Bindless slots); its specialization constants have no limit. The generated return types spell out each section's size, so a binding has no inline capacity and never allocates; the pipeline arrays are sized at init from the map.
- Matrices use column-major layout (`matrix_layout_column` in lava-build-slang's `compile.rs`, shared by the build and hot reload), so a glam `Mat4` arrives untransposed and shaders write `mul(M, v)`.
- Push-constant field types map like this: `Buf<T>` (a read-only `Ptr<T, Access.Read>`, so writing through it doesn't compile) /`MutBuf<T>` → `BufferSlice<T>`, a raw pointer `T*` → a `u64` address without an access (the shader clocks' `Clocks`), and `Img` (and `ImgArray`, 2D arrays, coordinates ending with the layer) → `impl image::SampledView<Dim = .., Format: HasTexels<[T; N]>> + 'a` (a view of the shape's dimension and a format of the shader's element type, turned into `view.handle::<K>()`, which panics unless the view is bound with the descriptors the shader reads): `Tex2D` reads through the sampler (`SampledView`, `ImageHandle<Sampled>`), `Image2D`/`MutImage2D` through the storage descriptor (`StorageView`, `ImageHandle<Storage>`), and `MutTex2D` reads through the sampler but writes as storage (`SampledView + StorageView`, `ImageHandle<Combined>`, an image bound with `bind_combined`). A typed load of a storage image costs several times a sampler fetch on Intel (it was a quarter of the tonemap, now the composite pass), so read an image through the sampler whenever its usage allows. Inside structs behind a `Buf`, `Img` fields become an `ImageHandle` of their kind and `DynImg` fields (also top-level ones, without accesses) an `ImageHandle` (`Dynamic`); `Img(handle)`/`DynImg(handle)` build them from a `uint`, and both have `IsNull()`. A `Sampler` (`bindless.slang`, one `u32`) is a `lava::bindless::SamplerHandle` anywhere, a plain value without accesses; `Img.Sample(sampler, uv)`, `SampleLevel(sampler, uv, level)`, `SampleCmp`/`SampleCmpLevelZero(sampler, uv, reference)` and `DynImg.Sample`/`SampleLevel` take one, with no default. `Accel` (a TLAS's address, `accel.get()` is the `RaytracingAccelerationStructure`) → `&Tlas`, a `u64` inside structs (pass `BufferAccess::trace(&tlas)` in the command's `Accesses`), never an `SCONST`. Slang structs that mirror a lava type (`MIRRORED_TYPES` in `codegen.rs`: `AccelerationStructureInstance` → `Instance` and `Sampler` → `SamplerHandle`, whose fields are public for the checks) aren't generated, only layout-checked. `Img` and `DynImg` have `GetDimensions()`. `DynImg` (`bindless.slang`) reads the sampled descriptor if its handle has one, else the storage one (nearest), else zero; the UI pass uses it for `UIVertex.texture`, and images referenced this way get no automatic barrier: pass them in the draw's `Accesses`. Slang numbers fragment outputs from location 0 whatever their `SV_Target` index, so a pass that writes attachments other than the first gives them `[[vk::location(n)]]`. Every pass is its own SPIR-V module, so passes can share entry points from an include (the scene passes' `scene_mesh`). A generated push-constant struct has every gap Slang leaves as a zeroed private `_pad` field (tail included), so it derives `Pod` without padding bytes and needs no SIMD alignment of glam's types. lava-build-slang rejects a pass with global parameters (descriptors, uniforms; the heaps aren't parameters) and push-constant structs or arrays that hold handles below the top level (they would be untracked).
- A ray tracing pass (`ray_tracing.slang` in lava-build-slang's `slang/`) has one raygen and any number of miss, hit (closest hit, any hit, intersection; procedural with an intersection shader) and callable entry points; `[Group(n)]` puts one at index n of its binding table region (the miss index, an instance's `sbt_offset`, the callable index; 0 without it, dense per region; hit entry points with the same index form one group), `[MaxRecursion(n)]` on the raygen sets the trace depth (0 to 31, 1 without it; a pass deeper than the device's `maxRayRecursionDepth` gets no pipeline and counts as missing what the device lacks, so recording it panics like a pass whose feature is missing). `compile::ray_tracing_groups` checks them, the pass table bakes them, and `layout_hash` covers them, so a hot reload that regroups is refused. Binding table records hold only handles, no shader record data.
- Specialization constants are baked into the pipeline, for values that are the same on every run (sizes, modes, device limits, a bindless handle that is fixed for the app's lifetime, like the font atlas's). Never put buffer addresses in them: an address differs from run to run, so Mesa's shader cache never hits and every start compiles the pipelines again (0.7 to 1.2 s here, against 0.1 ms cached), while the baked addresses gained nothing measurable. Declare them with `SCONST(T, name)` (`bindless.slang`; any `Img` alias, also `Buf`/`MutBuf`, which lava's test uses; always a `u64` constant, an image handle zero-extended, read back through `T.fromConst`) or a plain `[SpecializationConstant] const uint name = 0;`. They become the parameters of the generated `constant_bindings`, in id order, with the same accesses and barriers as push constants. Every pass keeps its pipelines in a map keyed by the constant bytes (laid out by `PassEntry.constants`; empty, and made at init, without constants; raster pipelines are keyed by raster state first; a key is copied to the heap only when its pipeline is made, a lookup takes the binding's bytes), so every new value builds a pipeline at first use, and a pass reaching 16 pipelines logs a warning: pass values that change on resize or per frame (frame-slot offsets, attachments, settings) as push constants.
- Pipelines (`lava/src/pipeline.rs`): per pass a `RwLock` of its shader module and one of its pipeline map (`PassPipelines`; no lock spans passes, and every lock ignores poisoning, since a creation that fails panics with no write guard held). A lookup takes the map's read lock; a miss read-locks the module, creates the pipeline outside the map's lock and inserts it under the write lock, keeping the module locked until then; if another thread inserted the key first, its pipeline is kept and the new one destroyed. `reload_pass` write-locks the module first and holds it through the rebuild, so no creation uses a module it destroys and every key is rebuilt. Every pipeline is made through one `VkPipelineCache`, loaded from `Config::pipeline_cache` at init (data of another device or driver, by its header, is ignored with a warning) and written back by `pipeline::save_cache()` (also called by `lava::shutdown`; through a `.tmp` file); init makes the unspecialised compute pipelines in one call and the ray tracing ones in another, and names every pipeline after its pass. A recording keeps its last bound compute and ray tracing pipeline (`Recording::bound_compute`/`bound_ray_tracing`): the same pass and constant bytes skip the lookup, the same pipeline the bind.
- Runtime hot reload is a debugging aid behind the `hot-reload` cargo feature of `core` and `game` (default on), which makes core depend on `lava-build-slang` with its `hot-reload` feature, so keep it simple rather than fast. The build script also writes `$OUT_DIR/lava/hot_reload.rs`, a `hot_reload::Build` (search paths, defines, optimization, watched directories, and per pass in map order its source and layout hash), which lava never sees. `lava_build_slang::watch!()`, which core calls right after `lava::init` (windowed and headless), includes it from the calling crate's `OUT_DIR`, watches its `watch_dirs` (the pass and include directories the build script was given) and lava-build-slang's `slang/`, and recompiles changed passes (a pass's `source` is its absolute path; any other changed file reloads every pass) with the same options on its own thread, then hands the SPIR-V to `lava::pipeline::reload_pass(index, spirv)`, which replaces the pass's module and pipelines in the `PipelineManager` (`lava/src/pipeline.rs`, the pass table types and every pass's pipeline cache) right away. There is one `PipelineManager`, which hands out copies of raw `vk::Pipeline`s (a ray tracing pass's as a `BoundRayTracing`, the pipeline and its binding table's regions); a reload swaps the new pipelines into its caches and retires the old ones, which are destroyed once no frame can use them (lifetime), so a recording that looked one up keeps using it. Without the feature nothing watches and nothing is ever replaced. Changing a push-constant or specialization-constant layout (or the entry points) still needs `cargo build` so the bindings get regenerated: `BuiltPass.layout` hashes them (`compile::layout_hash`) and a reload whose hash differs is refused with an error, as is one the driver rejects (nothing is replaced then); reloading rebuilds every cached specialization.

## Tests (lava, lava-macros, lava-build-slang, lava-tests)
- `cargo test -p lava -p lava-macros -p lava-build-slang -p lava-tests`. Add `-p lava-build-slang --features hot-reload` for the hot reload's watcher tests. Narrow with `-p lava --lib` (pure unit tests, no GPU), `-p lava-build-slang` (the compile helpers, plus the watcher with `--features hot-reload`), `-p lava-tests --lib` (the generated pass map), `-p lava-tests --test gpu_headless` (real GPU, headless, validation layer on, any validation error fails the test), `--test gpu_raster` (renderings and draws: indirect, indexed and multi-draws, draw parameters, depth bias clamps, per-draw scissors and viewports, render area offsets, vertex-only passes, stencil-only attachments, unordered accesses, array layers, layered and multiview renderings, dual-source blending, the draw state checks), `--test gpu_ray_tracing` (acceleration structures, ray queries and pipelines on a small scene, `lava-tests/shaders/include/ray_scene.slang`; skips without the features), `--test gpu_missing_features` (a context with `Config::disabled` set: the `MissingFeature` paths and baked draw state, the topology class included since no `dynamic-*` feature enables extended dynamic state 3, compared with `gpu_headless`'s goldens), `--test gpu_pipelines` (a context with a pipeline cache file: a foreign cache ignored, the saved one loaded by a child process of the test binary, threads making one new specialization at once, `reload_pass` swaps, refusals and races), `--test gpu_lifecycle` (no harness context: a failed init retried, `shutdown` refused while objects live, then init again, twice, with reclaim polling, dropped timelines' stamps, multi-waits and typed errors), `--test gpu_staging` (a context with only `rebar` disabled, so the harness timeline has a 1 MiB ring: drains, wrap-around, a full ring, threads, a transfer timeline's uploader releasing to graphics), or `--test gpu_window` (`PresentSurface`: acquire, present, recreation, images that stay current, misuse inside submissions and after `cmd.present`, present modes, composite alpha, HDR metadata, `present_all` of two windows, surface formats and their fallback; own `main`, opens windows briefly, skips without a display). Each feature compiles alone: `cargo check -p lava --lib --tests --no-default-features --features X` for every `X` and `assert-X` (a loop over the `[features]` of `lava/Cargo.toml`).
- lava's unit tests are all in `lava/src/tests.rs`, a few tests of logic worth checking (barriers and pending accesses, image states and ownership, the slot allocator, feature detection, queue families, GPU layouts); modules have no test modules of their own. Never construct a `Buffer`/`Image` or call `Ctx::*` there: `Ctx::get()` panics when lava isn't initialised.
- GPU tests share one context and one `Timeline<Graphics>` per test binary through `lava-tests/tests/common` (`gpu()` guard serialises tests and checks validation errors; `gpu.submit(|cmd: &mut Cmd| ..)` submits and blocks; `gpu.buffer(&data)` is a filled `Gpu` buffer, its copy drained and completed where the timeline has a ring (`gpu.uploader()`; the harness ring is 16 MiB, `common::staging(bytes)` before the first `gpu()` changes it); `common::panic_message(f)` returns what `f` panics with, for the tests of lava's checks; `common::nearest()` is a nearest, white-bordered `Sampler`'s handle; `common::disable(features)` before the first `gpu()` sets `Config::disabled`, `common::pipeline_cache(path)` `Config::pipeline_cache`). Bindless slots are allocated, so a test that checks slot reuse calls `lava::wait_idle()` first. A test that needs an optional feature skips (`SKIPPED ...` on stderr) where the device lacks it.
- **Lava's tests never use engine passes.** They live in `lava-tests`, an ordinary lava user: its `build.rs` compiles `lava-tests/shaders/*.slang` with lava-build-slang, and the tests import `lava_tests::bindings::*` and pass its `PASS_MAP` to `lava::init`. The generated bindings' tests (push constants, accesses) are in `gpu_headless.rs`, since slices and views need real buffers and images.
- `lava-tests/benches/recording.rs` (`cargo bench -p lava-tests --bench recording`, headless, validation off) times recording the test passes into real command buffers. Compare ratios between variants or alternating runs of two builds (`taskset -c 2`), not absolute times, which move with the CPU clock.
- Golden images live in `lava-tests/tests/golden/*.png`. A mismatch writes `<name>.actual.png`/`.diff.png` to `target/tmp/golden-failures/`. After an intended change to a test shader, re-bless with `LAVA_BLESS=1 cargo test -p lava-tests --test gpu_headless --test gpu_ray_tracing` and look at the PNGs.
- Slang gives shaders D3D-style `SV_VertexID`/`SV_InstanceID` (without `first_vertex`/`first_instance`); `SV_VulkanVertexID`/`SV_VulkanInstanceID` include them (`test_draw_params.slang`).

## Commands
- lava builds on stable Rust (Arch's `/usr/bin/cargo` or rustup's), edition 2024, with no `#![feature]`s; keep it that way.
- `ash` 0.38, `ash-window` 0.13 and `gpu-allocator` 0.28 come from crates.io, with no patches. ash 0.38 has headers 1.3.281, older than `VK_KHR_device_address_commands`, `VK_EXT_descriptor_heap` and `VK_EXT_depth_clamp_control`, so `lava/src/vk.rs` (`lava::vk`, also `lava::state::raw_vulkan`) re-exports `ash::vk` and adds their structs (layouts from the registry, ash 0.38's `TaggedStructure`/`Extends*` impls so `push_next` takes them), the `VkStructureType`/`VkDynamicState` values (`vk::DYNAMIC_STATE_DEPTH_CLAMP_RANGE_EXT`) and their device functions (`vk::device_address_commands::Device`, `vk::depth_clamp_control::Device`, loaded with `get_device_proc_addr`, only the commands lava records; a missing one panics naming it). Lava code uses `crate::vk`, never `ash::vk`. Add a newer extension there the same way, and delete the additions once an ash release has them. ash 0.38's `push_next` links the pushed struct's whole `p_next` chain, so a struct reused from an earlier chain must be unlinked first (`FeatureChain::chain` does). `shader-slang` and `shader-slang-sys` are slang-rs's crates.io release 0.1.0. Its reflection wrappers turn some null results of Slang's C API into references (undefined behaviour; slang-rs fixed it on main after the release), so lava-build-slang reads reflection only through `lava-build-slang/src/reflect.rs`: `checked_*` methods returning `Option`s that call the C API (`shader-slang-sys`, a direct dependency for this) where 0.1.0 doesn't check. Never call 0.1.0's `name`, `type_layout`, `element_type_layout`, `function`, `fields`, `parameters`, `entry_points`, `user_attributes`, `type_parameters`, `value_parameters` or `concrete_type` there. Generic type parameters are `Variable`s (0.1.0 mistypes them). Delete `reflect.rs` once slang-rs releases its fixed API. lava had its own forks of all four until 2026-10-16 and went back to upstream by choice.
- The Slang SDK lives in `slang-sdk/` (gitignored; the engine's `.cargo/config.toml` points at it too). Linking goes through `.cargo/config.toml`: `SLANG_DIR` for slang-rs's build script (bindgen, so it needs clang) and an absolute rpath to `slang-sdk/lib` for build scripts and hot-reload binaries, the setup lava-build-slang's README asks of every user. lava-build-slang's `build.rs` links `slang-compiler` explicitly because `-lslang` would pick up the unrelated S-Lang library.

- **Publishing** (nothing is published yet): `lava-macros`, `lava`, `lava-build-slang`, in that order; every dependency is on crates.io. Until `lava-macros` is published, `cargo package` can only verify it; `lava` and `lava-build-slang` need `--no-verify`/`--list`. The package name `lava` is taken by an abandoned crate whose owner was asked for it.
